# PA6 — Retrospective

**1. Slash Commands:** The most valuable slash command was `/fill-tests services/tasks.py` because it identified missing test coverage and added 17 new tests without changing production code. As recorded in `COMMAND_LOG.md`, the test suite increased from 280 to 297 passing tests. Compared with an ad hoc prompt, the slash command provided a reusable structure with a clear goal, project context, constraints, and verification steps. It also avoided duplicating existing tag and priority tests, making the results more focused.

**2. Hook Bypass Testing:** The most important finding was that having a hook configured does not mean every operation is protected. My first simulated Bash test using `echo test >> utils/errors.py` returned exit code 0, revealing that the hook checked dangerous commands but not output-redirection destinations. I added `is_protected_bash_write()` to inspect redirections and compare their destinations against protected paths. The retest returned exit code 2, and an actual Claude Code Bash attempt was also blocked. The case-variation test using `Utils/errors.py` was already blocked because the hook normalized Windows paths. These results showed why enforcement must be tested rather than assumed.

**3. CLAUDE.md Audit:** I kept architectural rules in `CLAUDE.md`, including the requirement that task business logic belongs in `services/tasks.py` rather than `routes/api.py`. This rule remains advisory because the current hook checks paths, command patterns, and content strings, not whether code follows the application's layered architecture. I would consider graduating a rule from `CLAUDE.md` to a hook when it is important, objective, repeatedly violated, and can be checked reliably from tool inputs. I removed the redundant instruction against modifying the AppError hierarchy in `utils/errors.py` because direct edits to that file are now blocked by the hook.

**4. Limits of PreToolUse:** One rule I would not try to enforce using the current PreToolUse hook is that every new endpoint must have meaningful test coverage. A PreToolUse hook sees an individual proposed tool operation, but it cannot reliably determine whether the completed feature has sufficient tests. I would enforce this through automated pytest checks in CI and use code review to assess whether the tests cover important behavior. This would complement the PreToolUse hook, which is better suited to rejecting specific prohibited operations before they execute.
